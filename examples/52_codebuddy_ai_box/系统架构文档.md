## 一、系统总览

CodeBuddy AI BOX 是一套「AI 编程助手 ←→ 硬件交互终端」的双向系统。核心能力：

- **上行（状态可视化）**：把 Claude Code 的实时工作状态（Token 用量、项目进度、AI 情绪、当前工具）推送到 ATK BOX 屏幕。
- **下行（决策/审批）**：AI 遇到岔路口时，把选择题推送到 ATK BOX，用户在触摸屏上点选，结果回传给 AI 继续执行。
- **音频 + 键盘**：ATK BOX 麦克风采集音频、按键 → 经 Dongle → USB 送到 PC（HID 键盘 + USB 声卡）。

### 端到端数据流

```
┌─────────────┐   USB Serial    ┌──────────┐   ESP-NOW 2.4G   ┌────────────┐
│     PC      │◄───────────────►│  Dongle  │◄────────────────►│  ATK BOX   │
│ (上位机工具) │   115200 8N1    │(ESP32-S3)│   Channel 1      │ (ESP32-S3) │
└─────────────┘                 └──────────┘                  └────────────┘
   Python 工具集                  USB 复合设备                   触摸屏 + 麦克风
   / GUI / MCP                    HID + UAC 声卡                 7 屏 LVGL UI
```

## 二、三层硬件架构

| 层 | 硬件 | 固件/软件 | 职责 |
|----|------|-----------|------|
| **PC 端** | 电脑 | Python 工具集 / `CodeBuddyBridge.exe` | 数据采集、协议封装、决策交互 |
| **中继** | Dongle (ESP32-S3) | ESP-IDF (`dongle_firmware/`) | USB↔ESP-NOW 双向转发、USB 声卡/键盘 |
| **终端** | ATK BOX (ESP32-S3) | Arduino (`51_mic_wifi.ino`) | 触摸屏 UI、麦克风、按键 |

## 二·五、ATK BOX 固件详解（终端层完整架构）

本章详细展开终端层的实现，包括 7 个 UI 界面、按键/触摸交互、硬件驱动、状态机逻辑。

### A. 七大 UI 界面（LVGL）

ATK BOX 运行 7 个全屏 LVGL 界面，按键 B (K1) 短按循环切换，顺序为 `{5→2→1→3→4→6→0}`。

| 界面 ID | 名称 | 主要内容 | 数据来源 | 交互能力 |
|---------|------|---------|---------|---------|
| **0** | ESP-NOW Status | 连接状态、丢包率、MAC 地址 | 本地统计 | 无（只读） |
| **1** | Token Usage | AI 服务 Token 用量（≤5 服务） | PC 推送 0x07 | ✅ 演示模式：A 短按高亮行 |
| **2** | Coding Status | 项目进度列表（≤6 项目） | PC 推送 0x08 | 无 |
| **3** | Product Inspo | 灵感卡片 + 打字机动画 | 演示数据 | ✅ 演示模式：A 短按重启动画 |
| **4** | User Profile | 用户照片 + 姓名 | SD 卡 `D:/user.png` | ✅ 演示模式：A 短按切换头像 |
| **5** | AI Status | 动画云朵 + 情绪表情 | PC 推送 0x09 或本地循环 | ✅ 点击触发情绪切换 |
| **6** | TouchTest | 触摸测试（坐标 + 绿点） | 实时触摸 | ✅ 画点验证触摸校准 |

**特殊界面**（不在循环中）：
- **界面 7**：**决策 UI**（Decision Request）- PC 推送 0x0A 时临时覆盖当前界面，显示标题 + ≤4 选项，用户触摸选择后发送 0x0B 回执，自动返回原界面。

#### A.1 界面 0 - ESP-NOW Status

**功能**：显示无线连接健康度，用于调试。

**显示内容**：
- 配对状态：`Paired` / `Not Paired`

- 本机 MAC 地址

**刷新**：每次界面切换更新一次。

#### A.2 界面 1 - Token Usage

**功能**：显示 AI 服务的 Token 配额消耗（最多 5 个服务）。

**数据格式**（0x07 帧）：

```c
typedef struct {

    uint32_t used;      // 已用 tokens
    uint32_t total;     // 总配额

```

**界面布局**：
- 标题："Token Usage"
- 列表：每行一个服务，显示 `[进度条] 服务名 used/total (xx%)`
- 进度条颜色：
  - 绿色 (< 50%)
  - 黄色 (50-80%)
  - 红色 (> 80%)

**演示模式交互**：
- **A 短按**：循环高亮下一行（高亮行背景变浅灰）
- **A 长按**：重置所有进度条到 10%

#### A.3 界面 2 - Coding Status

**功能**：显示多个项目的实时进度（最多 6 个）。

**数据格式**（0x08 帧）：

**状态码映射**：

#### A.6 界面 5 - AI Status（启动默认界面）

**功能**：实时显示 AI 工作状态，用动画云朵 + 表情表达情绪。

**三种情绪**：

| 情绪 | 枚举值 | 眉毛 | 嘴巴 | 默认文字 | 触发场景 |
|------|--------|------|------|---------|---------|
| THINKING | 0 | 上扬（Y-4px） | 小闭嘴 | "Thinking..." | 用户提交 prompt |
| CODING | 1 | 皱眉（Y+5px） | 动嘴说话（每 250ms 开合） | "Coding..." | 工具执行中 |
| DONE | 2 | 平眉（Y±0） | 宽笑脸（26×14px） | "Done!" | 任务完成 |

**数据来源**：
- **本地模式**（默认）：每 4 秒自动循环切换情绪（THINKING → CODING → DONE → 回到 THINKING）
- **外部模式**：收到 PC 的 AI Emotion 帧（0x09）后覆盖本地循环，15 秒无新帧则恢复本地

**0x09 帧结构**：
```c
typedef struct {
    uint8_t frame_type;    // = 0x09
    uint8_t emotion;       // 0/1/2
    uint8_t seq_num;
    char text[20];         // 自定义文字（为空则用默认）
    uint8_t crc8;
} ai_state_frame_t;
```

**动画细节**：
- 眼睛每 3 秒眨一次（闭眼 100ms）
- CODING 状态下嘴巴每 250ms 开合（模拟说话）
- 刷新频率：100ms 定时器

**触摸交互**：点击云朵区域 → 手动切换到下一个情绪。

#### A.7 界面 6 - TouchTest

**功能**：触摸硬件调试工具，用于校准坐标映射。

**显示内容**：
- 实时坐标：`X: 123  Y: 456`
- 绿色圆点：跟随手指位置移动（直径 20px）
- 松开显示：`Released`

**用途**：
- 验证触摸芯片工作正常
- 校准 `TOUCH_SWAP_XY`/`FLIP_X`/`FLIP_Y` 宏
- 测试触摸灵敏度

**进入方式**：
- 按键 B 循环切换到此界面
- BOOT 按键长按直达（快捷键）

#### A.8 界面 7 - Decision UI（临时覆盖界面）

**功能**：显示 PC 推送的决策请求，等待用户触摸选择。

**触发**：收到 PC 的 Decision Request 帧（0x0A）。

**界面布局**：
- 背景：半透明遮罩覆盖当前界面
- 标题：居中显示（≤32 字符）
- 选项：最多 4 个按钮（每个 ≤24 字符），竖向排列
- 按钮样式：灰色背景，触摸时高亮

**交互流程**：
1. PC 发送 0x0A → ATK BOX 切换到 Screen 7
2. 用户触摸某个选项 → 按钮高亮 → 发送 0x0B 回执（chosen_index）
3. 自动返回之前的界面

**超时机制**：30 秒无操作 → 发送 `chosen=0xFF`（取消）→ 返回原界面。

### B. 按键交互设计（4 键布局）

ATK BOX 有 4 个物理按键，但只有 3 个软件可读（RST 是硬件复位）。

| 按键 | 硬件连接 | 软件可读 | 短按 (<0.6s) | 长按 (≥0.6s) |
|------|---------|---------|--------------|--------------|
| **KEY1 (A/K2)** | XL9555 P0.3 | ✅ | F2 + 切换音频流 | Enter 确认 |
| **KEY0 (B/K1)** | XL9555 P0.4 | ✅ | 切换到下一个界面 | 连续 Backspace (100ms 间隔) |
| **BOOT (K0)** | GPIO0 | ✅ | 返回主界面（AI Status） | 跳转触摸测试界面 |
| **RST** | EN Pin | ❌ | 硬件复位 | 硬件复位 |

**组合键**：
- **A + B 同时按 2 秒**：触发**演示模式**（注入模拟数据到 Token/Project/Inspo 界面）

**注意**：BOOT 按键在启动时按住会进入下载模式，不要在开机/复位时按住。

#### B.1 按键去抖与状态机

```cpp
const uint32_t LONG_PRESS_MS = 600;         // 长按阈值
const uint32_t REPEAT_INTERVAL_MS = 100;    // B 长按重复间隔
const uint32_t DEMO_TRIGGER_MS = 2000;      // A+B 演示触发

static bool prev_a, prev_b, prev_boot;
static uint32_t press_time_a, press_time_b, press_time_boot;
```

**按键 A 逻辑**（HID 键码在 `espnow_protocol.h`）：
- 按下 → 记录时间戳
- 释放 → 判断持续时间：
  - < 600ms → 短按：发送 F2 (0x3B) + 切换音频流
  - ≥ 600ms → 长按：发送 Enter (0x28)

**按键 B 逻辑**：
- 释放时持续 < 600ms → 短按：切换界面（`order_index = (order_index + 1) % 7`）
- 按住时持续 ≥ 600ms → 长按：每 100ms 发送一次 Backspace (0x2A)

### C. 触摸交互（CHSC5432 驱动）

**触摸芯片**：CHSC5432 电容触摸 IC，I2C 地址 0x2E。

**坐标校准**（`AtkBoxTouch.h`）：
```c
#define TOUCH_SWAP_XY   0   // ATK BOX 验证值：0（不交换 X/Y）
#define TOUCH_FLIP_X    0   // X 镜像
#define TOUCH_FLIP_Y    0   // Y 镜像
```

**复位控制**：通过 XL9555 P0.6 控制 CHSC5432 的 RST 引脚（初始化时拉低 10ms 再拉高）。

**读取流程**：
1. I2C 读取 0x00 寄存器（4 字节地址，32 位寄存器协议）
2. 解析 `point_num`（触摸点数）
3. 读取 X/Y 坐标（10 位，0-1023）
4. 映射到 LCD 分辨率 `(X*240/1024, Y*320/1024)`

**触摸用途**（2026-08-31 交互定稿）：
- ❌ ~~左右滑动切换界面~~（已移除，改由按键 B 短按）
- ✅ 界面内点击：详情卡片、AI 情绪切换、按钮点击
- ✅ TouchTest 界面画点验证
- ✅ Decision UI 触摸选项按钮

### D. 音频系统（ES8311 + I2S）

**音频芯片**：ES8311（I2C 地址 0x18），支持麦克风录音 + 喇叭播放。

**I2S 配置**：
- 采样率：16kHz
- 位深：16bit
- 通道：单声道（录音时读双声道后下混为单声道）
- DMA 缓冲：128 字节 = 64 采样点 = 4ms @ 16kHz

**音频流发送**：
1. I2S 录音 → `stereoBuf[128 个 int16]`
2. 下混为单声道 → `monoBuf[64 个 int16]`
3. 封装为 ESP-NOW Audio 帧（0x02）→ Dongle
4. 序列号自增（0-255 循环），用于丢包检测

**喇鸣器（Beeper）**：
- XL9555 P0.2 控制，ATK BOX 上电默认高电平（持续鸣叫）
- 固件初始化时设为**输入模式**（高阻态）→ 静音

**提示音**（计划功能，未完全实现）：
- 开始录音：440Hz 80ms
- 发送完成：880Hz 60ms
- 审批提醒：660Hz 100ms×2
- 任务完成：523Hz 150ms
- 拒绝/错误：220Hz / 330Hz

### E. SD 卡图片系统

**SD 卡规格**：
- **文件系统**：必须 FAT32（64GB+ 默认 exFAT 不兼容，需重新格式化）
- **挂载点**：LVGL 'D:' 盘符（自定义 `lv_fs_sd_init()` 实现）

**图片路径**：
- 用户头像：`D:/user.png`, `D:/user1.png` ... `D:/user9.png`（最多扫描 10 张）
- AI 云朵背景：`D:/ai.png`

**PNG 解码缓存**（`lv_conf.h`）：
```c
#define LV_IMG_CACHE_DEF_SIZE 4   // 关键：必须 ≥1
```
**影响**：
- `=0` → 每帧重新解码 PNG（100+ms），导致按键响应慢、界面卡顿
- `≥1` → 缓存解码结果，流畅 60fps

**Fallback 方案**：SD 卡图片缺失时使用渐变色块（蓝紫渐变 `lv_grad_color()`）。

## 三、PC 端软件架构（重点）

PC 端是本次文档的核心。所有工具围绕**一个独占串口的守护进程**（daemon）展开，采用「**daemon + 多客户端**」的分层设计。

### 3.1 分层图

```
┌──────────────────────────────────────────────────────────────┐
│                        客户端层 (Clients)                       │
├────────────┬───────────────┬──────────────┬───────────────────┤
│ hook_client│ mcp_atkbox_   │ guess_number │ realtime_monitor  │
│   .py      │  server.py    │  _game.py    │   .py (可独立)     │
│(Claude Hook)│ (MCP 工具)   │  (游戏)      │  (状态推送)        │
└──────┬─────┴───────┬───────┴──────┬───────┴─────────┬─────────┘
       │             │              │                 │
       └─────────────┴──────────────┴─────────────────┘
                            │ TCP JSON  127.0.0.1:47100
                            ▼
┌──────────────────────────────────────────────────────────────┐
│              atkbox_daemon.py  (守护进程，独占串口)             │
│  ┌────────────────┐  ┌──────────────┐  ┌────────────────────┐ │
│  │ IPC Server     │  │ 后台推送线程  │  │ 决策/审批阻塞处理   │ │
│  │ (TCP 47100)    │  │ Token/Project │  │ (等回执)           │ │
│  └────────────────┘  └──────────────┘  └────────────────────┘ │
│                            │                                    │
│                    ┌───────▼────────┐                          │
│                    │ SerialManager  │  串口独占 + 断线重连      │
│                    │ (serial_mgr)   │                          │
│                    └───────┬────────┘                          │
└────────────────────────────┼──────────────────────────────────┘
                             │ COM6 @ 115200
                             ▼
                          Dongle
```

### 3.2 关键设计：为什么要 daemon？

**串口只能被一个进程独占**。如果每个工具都直接开 COM6，就会互相抢占报 `PermissionError`。
因此引入 daemon：**唯一持有串口的进程**，其他工具都通过 TCP IPC（`127.0.0.1:47100`）向它发请求。

> ⚠️ **重要区分**：`mcp_atkbox_server.py` **不是** daemon，它是 MCP stdio 客户端，
> 自己去连 47100。「MCP 工具能用」不等于「daemon 在跑」——daemon 需单独启动
> （或由 `CodeBuddyBridge.exe` GUI 托管）。

### 3.3 IPC 协议（TCP 47100）

单行 JSON，请求/响应模式。三种请求类型：

| type | 请求示例 | 响应 | 行为 |
|------|---------|------|------|
| `status` | `{"type":"status","state":"THINKING","tool":"Read","detail":"x.py"}` | `{"ok":true}` | 非阻塞，带 1s 节流 |
| `decision` | `{"type":"decision","title":"...","options":["A","B"]}` | `{"ok":true,"chosen":0-3}` | 阻塞等回执（≤40s），255=取消 |
| `approval` | `{"type":"approval","tool":"Write","file":"x.py","preview":"..."}` | `{"ok":true,"decision":"allow"/"deny"}` | 阻塞等回执 |

## 三·五、两大客户端功能详解（Hook / MCP）

客户端层最重要的两个入口是 **Claude Hook**（`hook_client.py`）和 **MCP 工具**（`mcp_atkbox_server.py`）。两者定位不同：Hook 是「被动监听」Claude 的运行事件自动推送状态/拦截审批；MCP 是「主动调用」的工具，让 Claude 显式地在硬件上问用户问题。

### A. Claude Hook 客户端（hook_client.py）

**定位**：一个"瘦客户端"。它本身不碰串口，只负责把 Claude Code 触发的 Hook 事件翻译成 IPC 请求发给 daemon。每次 Hook 触发都是一次性进程（启动 → 连 47100 → 发请求 → 退出）。

**调用方式**：`python hook_client.py <event_type>`，Claude Code 通过 **stdin 传入 JSON**（包含 prompt、tool_name、tool_input 等）。

#### A.1 四个正式 Hook 事件

| 事件 | Claude 触发时机 | hook_client 行为 | 发送的 IPC | 是否阻塞 |
|------|----------------|-----------------|-----------|---------|
| **user_prompt** | 用户提交一条 prompt | 取 prompt 前 50 字 → 发 THINKING 状态 | `status/THINKING` | 否（静默退出） |
| **pre_tool** | 工具执行**前** | 见下方拦截逻辑 | `approval` 或 `status` | Write/Edit 类阻塞 |
| **post_tool** | 工具执行**后** | 提取目标文件/命令 → 发 RUNNING 状态 | `status/RUNNING` | 否 |
| **stop** | 一轮任务完成 | 发 DONE 状态 | `status/DONE` | 否 |

**状态流转效果**：用户提问 → BOX 显示 `THINKING`（思考）→ 每次工具调用 → 显示 `RUNNING + 工具名`（工作中）→ 任务结束 → 显示 `DONE`（完成）。ATK BOX 的 AI 云朵表情随之切换。

#### A.2 pre_tool 的审批拦截（核心安全能力）

`pre_tool` 事件里对**写操作工具做拦截**（`matcher: "Write|Edit|NotebookEdit"`）：

1. 提取 `file_path`（或 notebook_path）和 `content` 前 200 字作为预览
2. 向 daemon 发 `approval` 请求（**阻塞等待**用户在 BOX 上批准/拒绝）
3. 根据回执输出 Claude Code 的权限决策 JSON：
   - 批准 → `{"permissionDecision": "allow"}`（工具正常执行）
   - 拒绝 → `{"permissionDecision": "deny"}`（工具被阻止）

> 这意味着：**AI 每次要写文件，都会先在你的硬件盒子上弹出审批**，你点"允许"它才写。daemon 侧还会按文件路径推断风险等级（test→低，config/settings→中，其余→高）。

#### A.3 AskUserQuestion 监测

当 Claude 调用内置的 `AskUserQuestion` 工具时，hook 会**监测但不拦截**：把问题数量记到日志、发一条 RUNNING 状态，然后放行（不输出 JSON = 默认 allow）。这是为将来"把 Claude 的提问自动转到硬件"预留的探针。

#### A.4 实验事件探针

代码里还有一批实验性事件处理（`notify_agent_input`、`elicitation`、`permission_request` 等），作用是**探测 AskUserQuestion 到底触发哪个 hook**——把完整 `hook_input` 记进 daemon 日志和 stderr，不干预流程。属于研发调试用，正式功能不依赖。

#### A.5 Hook 安装（install_hooks.py）

- 把 4 个 hook（UserPromptSubmit / PreToolUse / PostToolUse / Stop）**合并**进 `~/.claude/settings.json`，保留用户已有字段
- 安装前自动备份为 `settings.json.backup`
- `--uninstall` 可干净移除
- **PyInstaller 兼容**：打包成 exe 后，`__file__` 指向临时目录 `_MEIxxx`（exe 退出即消失）。安装脚本会把 `hook_client.py` 复制到永久目录 `~/.codebuddy_bridge/`，再把该永久路径写进 settings，避免 exe 关闭后 hook 失效。

### B. MCP 工具服务（mcp_atkbox_server.py）

**定位**：一个 **MCP stdio server**，向 Claude 暴露一个可主动调用的工具 `ask_on_atkbox`。与 Hook 相反，这是 Claude "想问就问"的主动通道。

> ⚠️ 再次强调：MCP server **不持有串口**，它也是 daemon 的客户端，收到调用后连 47100 转发 `decision` 请求。

#### B.1 暴露的工具：ask_on_atkbox

| 项 | 规格 |
|----|------|
| 功能 | 在 ATK BOX 硬件上显示一道选择题，等用户触摸选择 |
| 入参 | `title`（≤31 字符）、`options`（1-4 项，每项 ≤23 字符） |
| 返回 | 用户所选项的索引 0-3 及文本；255 = 取消/超时 |
| 超时 | 40 秒 |
| 语言 | **仅英文**（中文触发编码 bug） |

#### B.2 实现的 MCP 协议方法

server 是一个 stdin 逐行读 JSON-RPC 的循环，实现了标准 MCP 握手：

| 方法 | 作用 |
|------|------|
| `initialize` | 返回协议版本 `2024-11-05`、serverInfo（name=atkbox）、capabilities |
| `tools/list` | 列出唯一工具 `ask_on_atkbox` 及其 inputSchema（title + options 的类型约束） |
| `tools/call` | 执行调用：连 daemon 发 decision → 拿 chosen → 组装成人类可读的 content 文本返回 |
| 未知方法 | 返回 `-32601 Method not found` |

#### B.3 调用链

```
Claude 决定问用户 → tools/call ask_on_atkbox(title, options)
  → send_decision_to_daemon() 连 127.0.0.1:47100
    → daemon 发 0x0A → Dongle → BOX 显示 Screen 7
      → 用户触摸 → BOX 发 0x0B → daemon → MCP
        → 返回 "User chose option N: <文本>" 给 Claude
```

#### B.4 MCP 安装（install_mcp_atkbox.py）

- 写入 `~/.claude.json` 的 `mcpServers` 字段（Claude Code 2.1.206+ 实际读取位置）
- 配置形如 `{"atkbox": {"command":"python","args":[server路径],"type":"stdio"}}`
- 同样有 **PyInstaller 永久化**逻辑：把 `mcp_atkbox_server.py` 复制到 `~/.codebuddy_bridge/`
- 安装后需**完全重启 Claude Code**（exit 所有窗口再启动），`/mcp` 验证工具出现

### C. Hook vs MCP 对比

| 维度 | Hook (hook_client.py) | MCP (mcp_atkbox_server.py) |
|------|----------------------|----------------------------|
| 触发方 | Claude 运行事件（被动） | Claude 主动调用工具 |
| 主要能力 | 状态可视化 + 写操作审批拦截 | 决策选择题 |
| 生命周期 | 每事件一次性进程 | 常驻 stdio server |
| 阻塞 | 仅审批阻塞 | 决策调用阻塞（≤40s） |
| 配置位置 | `~/.claude/settings.json` hooks | `~/.claude.json` mcpServers |
| 与 daemon 关系 | 客户端（发 status/approval） | 客户端（发 decision） |

## 五、通信协议规范

### 5.1 串口帧格式（PC ↔ Dongle）

```
┌──────┬──────┬─────────┬─────────────┬───────────┐
│ 0xA5 │ 0x5A │ len(1B) │  payload    │ outer_crc8│
└──────┴──────┴─────────┴─────────────┴───────────┘
                          └─ ESP-NOW payload (含 inner_crc8)
```

- **双层 CRC8**（多项式 0x07）：外层校验串口传输，内层校验 ESP-NOW 载荷。
- **帧间延迟**：连续发送需间隔 0.5s，Dongle 转发无缓冲。

### 5.2 帧类型总表（espnow_protocol.h）

| 帧类型 | 值 | 方向 | 用途 |
|--------|-----|------|------|
| KEY | 0x01 | BOX→PC | 按键事件（HID） |
| AUDIO | 0x02 | BOX→PC | 音频数据（16kHz 单声道） |
| FEC | 0x03 | BOX→PC | 音频 XOR 冗余包 |
| PAIR / PAIR_ACK | 0x04/0x05 | 双向 | 配对握手 |
| HEARTBEAT | 0x06 | 双向 | 心跳 |
| TOKEN_STATUS | 0x07 | PC→BOX | Token 用量（≤5 服务） |
| PROJECT_STATUS | 0x08 | PC→BOX | 项目进度（≤6 项目） |
| AI_STATE | 0x09 | PC→BOX | AI 情绪（驱动云朵表情） |
| DECISION_REQ | 0x0A | PC→BOX | 决策请求（标题 + ≤4 选项） |
| DECISION_REPLY | 0x0B | BOX→PC | 决策回执（0-3 或 0xFF） |
| AGENT_STATUS | 0x0C | PC→BOX | Agent 工作状态可视化 |
| AGENT_APPROVAL_REQ | 0x0D | PC→BOX | Agent 审批请求 |
| AGENT_APPROVAL_REPLY | 0x0E | BOX→PC | Agent 审批回执 |

## 七、已知陷阱（踩坑记录）

| # | 问题 | 原因 | 解决 |
|---|------|------|------|
| 1 | `PermissionError(13)` | 多进程抢串口 | 统一走 daemon IPC，不直接开串口 |
| 2 | MCP 能用但游戏连不上 | daemon 没启动 | 先启 daemon 或开 GUI |
| 3 | 中文选项 `surrogates not allowed` | MCP 编码 bug | 标题/选项只用英文 |
| 4 | 控制台 emoji 崩溃 | Windows GBK | 脚本开头强制 UTF-8 wrapper |
| 5 | "Frame length mismatch" | 缺 seq_num | 状态帧需 3 字节头 `[type,count,0]` |
| 6 | "Stuck in S_CRC" | 缺外层 CRC | `wrap_frame()` 追加 `crc8(payload)` |
| 7 | 只有首帧显示 | 无帧间延迟 | 连续发送加 `time.sleep(0.5)` |

## 十、技术亮点与创新

### 1. 双向硬件交互（行业首创）

传统 AI 编程助手只有单向输出（终端文字）。本项目实现**双向硬件交互**：

- **上行**：状态可视化（Token/项目/AI 情绪实时同步到触摸屏）
- **下行**：决策/审批（AI 在硬件上问问题，用户触摸回答）

**价值**：
- 降低注意力切换成本（余光扫一眼盒子就知道 AI 在干嘛）
- 提升安全性（写文件前必须在物理设备上批准）
- 增强沉浸感（云朵表情跟随 AI 工作节奏变化）

### 2. daemon + 多客户端架构

解决**串口独占冲突**的优雅方案：

```
单一守护进程持有串口 → 所有工具通过 IPC 共享
```

**优势**：
- Hook、MCP、监控脚本、游戏工具同时运行互不干扰
- 断线重连集中处理，客户端无需关心
- 后台推送与实时交互并行，无性能瓶颈

### 3. PyInstaller 永久化方案

打包 exe 后 `__file__` 指向临时目录 `_MEIxxx`，hook/MCP 脚本随 exe 退出消失。

**创新解决**：
- 检测 `sys.frozen` 标志
- 自动复制脚本到 `~/.codebuddy_bridge/`
- settings.json 写入永久路径
- exe 可关闭，hook 持久生效
